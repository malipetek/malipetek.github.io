# AGENTS.md

## One site, one Worker — plus the portal's home on a third host
- **lab.malipetek.dev** is the developer lab and the only site left on this Worker: `/kb/*`, `/plugins/*`, `/plugins.json`, `/blog/*`, `/experience/*`, `/projects/*`, `/pdfextractor/*`, and its own KB MCP at `/mcp` (proxied to `/kb-mcp` on the intercom Worker).
- **malipetek.dev** is the lab's front door: `/portal*`, `/mcp` and `/.well-known/*` 301 to ptechsolutions.net, the lab's own paths 301 to `lab.malipetek.dev`, the retired contracting pages (`/contact`, `/agents`, legal, `/<code>/…`) 301 to `https://ptechsolutions.net/`, `/api/*` stays (the intercom backend this Worker proxies), and everything else 301s to the lab.
- **ptechsolutions.net** is the portal's public home and lives in a different repo: `github.com/PTechGroup/ptechsolutions` (`~/Documents/Documents/Projects/ptechsolutions-site`). Two Workers deploy from it — `ptechsolutions` (the PTech homepage at `/`, proxies portal paths over a `PORTAL` binding) and `ptech-portal` (the Astro-built portal pages + proxy of `/api`, `/mcp`, OAuth `/.well-known` to `malipetek-intercom` over `INTERCOM`). Portal JS calls `https://ptechsolutions.net/api` same-origin; `ptechsolutions.net` is in the intercom's `ALLOWED_ORIGINS` and the Turnstile sitekey lists it.
- The portal source was ported out of this repo; the copies under `src/pages/portal`, `src/components/portal`, `packages/admin-ui` and the portal's `src/lib`/`src/i18n`/`src/styles` files are dead code kept only until they are stripped. The i18n catalogs still drift: `i18nSync` commits translations to THIS repo, not to ptechsolutions-site.
- The rule set is `src/lib/siteHosts.ts`, called from `src/middleware.ts` for server routes and from `src/worker.ts` before the adapter serves a prerendered page. A prerendered page never reaches Astro middleware, even with `run_worker_first`, so the worker entry exists; the prerendered paths that need a redirect are listed in `run_worker_first` in `wrangler.jsonc`.
- `llms.txt`, `robots.txt`, `sitemap.xml` and `sitemap-index.xml` are server routes and answer per Host. Do not add a static `public/robots.txt` or `public/llms.txt`; assets are served before the Worker.

## Client portal
- `/portal` (and `/portal/ticket`, the address in emails) mount `src/components/portal/ClientPortal.jsx`: React, hash routes (`#/ticket/12`), styles in `src/styles/client-portal.css`. The overview's 3D board is `initBoard` in `src/lib/workshop3d.ts` (the homepage machine with the client's own requests on it). Signed out, `/portal` is the same workspace with the homepage's own 3D workshop and the sign-in card in it (`src/components/portal/Guest.jsx`). Adding a project is the portal route `#/new` (`src/components/portal/Intake.jsx`); the old `/portal/start` 301s there (`MOVED` in `src/lib/siteHosts.ts`).
- Ali invites a client to existing projects in Admin → Clients → **Invite client** (`POST /admin/clients`): the account is made only if the email is new (never promoted, renamed or re-languaged if it exists), the projects are attached idempotently, and a 7-day one-time link (`login_tokens.purpose = 'invite'`, migration `0037_invites.sql`) signs them in through `/portal/verify`. Resend replaces the unused links, Revoke kills them; `GET /admin/clients` carries `invitedAt`, `pending` and `inviteExpiresAt`.
- Projects are managed by hand in Admin → Clients & projects: **Edit** renames a project or changes its kind (`PATCH /admin/projects/:id`; the slug never changes), and each card's **People** list adds several addresses at once (each one is an ordinary invite, `POST /admin/clients` with `copy`), removes them, and switches **all emails** per person (`PUT /admin/clients/:userId/projects/:projectId { copy }`, `user_projects.copy_mail`, migration `0038_project_copies.sql`). With it on, that person gets a copy of every client request's emails on the project (new request, Ali's replies, status changes; `mailCopies` in `worker/src/portal.ts`) in their own language, with no Reply-To and no bill.
- A client reads every client request on the projects attached to them, not only the ones they filed: `VISIBLE_TICKETS` in `worker/src/portal.ts` scopes the list, thread, files and overview counts, while `/auth/verify` only ever raises `ADMIN_EMAIL` to admin and never changes an existing account's role. A project-mate's request is read-only (no reply, withdraw, move or budget) and its price, time, AI cost and budget are stripped; requests with no project stay private to their author, and `kind = 'system'` work stays Ali's.

## Languages (i18n)
- Locales: `src/lib/locales.js` (35, English source). Clients pick theirs in the portal (globe button) → `users.locale` + `users.translation` (`deepseek | cloudflare | off`); Ali can set both in Admin → Clients.
- Ticket bridge: `worker/src/translate.ts`. Client messages are translated to English for Ali, his email and the agent brief; Ali's replies are translated into the client's language. Originals are never changed; translations live in `message_translations` (migration `0025_i18n.sql`). DeepSeek is the main engine (secret `DEEPSEEK_API_KEY`), Workers AI m2m100 (`AI` binding) the fallback. System lines stay English in the database and are translated in the portal by `systemLine` in `TicketView.jsx`.
- Interface strings: `src/i18n/messages/<locale>.json`, English in `en-US.json`, `t()` from `useT()` in the portal. After adding or changing English keys, nothing to run: the Worker translates them itself (`worker/src/i18nSync.ts`, its own `DEEPSEEK_API_KEY`). Admin → Settings → Translations → **Translate now** asks for a run on the next five-minute tick: it translates the missing or re-worded keys in every locale and commits the catalogs, their meta and `src/i18n/mail.js` to master through the GitHub App (installation on `@malipetek`), which deploys like any push. It is by hand on purpose (copy changes many times before it is translated once): the cron only checks master's `en-US.json` every 15 minutes so the panel can say English changed; the panel's **Translate automatically** switch (`i18n_sync_auto`, off by default) makes the cron run it on every change. The logic both share is `src/lib/i18nSync.js`; `node scripts/i18n-sync.mjs` still works by hand (`--check` reports, `--bundle` rewrites `mail.js`).
- Site: the homepage, `/contact` and `/agents` exist once per locale (`/`, `/tr/`, `/tr/contact`, `/de-DE/agents`; English stays unprefixed). `src/components/Home.astro`, `ContactPage.astro` and `AgentsPage.astro` hold the markup and take a `t`; `src/lib/site.js` builds it from the same catalogs (`site.*` keys, plus `offer.*` for the copy that lives in `src/lib/offer.js`) and `localizedPath(code, path)` names a page's URL in a language. `Base.astro` takes `locale`, `path` and `languagePicker` and emits the canonical, the full hreflang set and `og:locale` alternates from that path, so the picker and the suggestion banner point at the same page. `/en-US/...` is a 404. The legal pages stay English and carry no hreflang.

## Marketing automation
- Desk: **Admin → Marketing** (`packages/admin-ui/src/marketing.jsx`); API and the send engine in `worker/src/marketing.ts`, schema in migration `0023_marketing.sql`.
- Email goes out from `hello@malipetek.dev` on the 5-minute cron, through Cloudflare's `MARKETING` binding or Amazon SES (`worker/src/ses.ts`, SigV4 over fetch; desk Settings → Sender). SES is us-east-1, production access, 50k/day, 14/s, DKIM on malipetek.dev; the Worker needs secrets `AWS_SES_ACCESS_KEY_ID` + `AWS_SES_SECRET_ACCESS_KEY`. Replies, opt-outs, bounces (DSN) and spam complaints (ARF; SES feedback forwarding) come back through the `hello@` branch of `worker/src/inbound.ts`. Every email has a one-click `List-Unsubscribe` (`/api/marketing/u/:id/:sig`). The cron pauses the desk and mails Ali when 14-day bounces pass 4% or complaints 0.2% (`judgeHealth`). Contacts carry `source_kind` (Sources tab: rates per list) and `country` (consent-only countries in `CONSENT_COUNTRIES` are never mailed). Queued emails can be previewed, test-sent and rewritten by hand in the Email tab; a hand edit (`edited_at`) survives **Re-render scheduled**.
- X/LinkedIn: `marketing/publisher` posts queued drafts from a real Chrome profile (no paid API), polled every 15 minutes by launchd, bearer `MARKETING_TOKEN` on `/marketing/publisher/*`.
- Voice: anything public in our name goes through `marketing/style/README.md` (vendored humanizer + stop-slop skills; mark the tells, rewrite, score 40/50). `content.ts` `SLOP` refuses posts with em dashes, not-X-but-Y, throat-clearing, stock AI words or invented audiences. The category is **vibe contracting** (`marketing/kit.md` → "The name").
- Email copy: `SEQUENCES` in `worker/src/marketing.ts` is the source; a step with `plain` is used when the contact has no observation. After editing it, run `node --experimental-strip-types --no-warnings scripts/build-outreach.mjs` in `worker/` and press **Re-render scheduled** (or `POST /admin/marketing/messages/rerender`, optional `{from, to}` to move queued mail between sequences).
- Desk tabs: Overview (14-day sends/replies/bounces per local day, everything that came back), Contacts (200 per page, bulk pause/opt-out, click a row for the full history), Email, Posts, Sequences, Sources, Settings. **Review next** steps through the next first emails (`GET /admin/marketing/review`, `POST …/messages/:id/review`); with Settings → Review first emails on, a first email only sends once reviewed or hand-edited (`reviewed_at`, migration 0034).
- Posts: with Settings → Approval on (default), the cycle's posts land as drafts holding their slot and Ali gets them by email; **Approve** in the Posts tab schedules them. Every post the publisher reports is mailed to Ali with its text and URL.
- Writing the posts: no one does it by hand. The five-minute cron (`ensureContentCycle` in `worker/src/content.ts`) files an approved system ticket on `malipetek-dev-site` when the queue is thin; a fleet agent writes 2 X + 1 LinkedIn post and ends with an `<<<OUTBOX` JSON block; `finishContentCycle` (called from `node.ts` and portal `run-result`) checks and schedules them Tue/Thu/Sat. The last dozen posts in `marketing_messages` are the agent's memory — the brief lists them — and the desk's Marketing → Settings → Voice notes are appended to every brief.
- Prospects: `marketing/prospector/extract.mjs` reads only the URLs it is given; `marketing/prospector/directory.mjs` crawls one directory within robots.txt, depth and page budget; `marketing/prospector/osm.mjs` turns an OSM state file (`--pbf`, offline via `osmium`) or one Overpass query into business websites; `marketing/prospector/bulk.mjs` reads those homepages (`collect`) and has Jev/TypeSafe keep the US small businesses (`qualify`); `marketing/prospector/verify.mjs` drops addresses whose domain has no MX before import. `emailsIn` also decodes Cloudflare-obfuscated addresses (`data-cfemail`) and JSON-LD `email`; `osm.mjs` writes businesses with an email and no website to `osm-<scope>-mail-only-<day>.csv` for the **No website** sequence. Setup order, gates and compliance: `marketing/automation.md`.

## SEO desk
- Desk: **Admin → SEO** (the view lands in `packages/admin-ui/src/seo.jsx`); the audit, the GEO probe, the citation check and the fix cycle are all in `worker/src/seo.ts`, schema in migration `0036_seo.sql`. The desk only ever reads our own two hosts (`SEO_HOSTS`), never a client site.
- Daily audit: the five-minute cron (`runSeo`) reads each host's `sitemap-index.xml` (or `sitemap.xml`), following the index, then up to 200 pages (the whole of both sites today), and writes one `seo_pages` row per page per day: title, description, canonical, hreflang, JSON-LD `@type`s, h1 count, internal links, bytes, ms, sitemap/llms coverage, a 0–100 `score` from `SCORE_WEIGHTS`, and the page's issues. `seo_findings` holds one row per host+path+code; an audit that no longer sees one sets `resolved_at`, seeing it again clears it and keeps `first_seen`. Only a page that answered is audited, so a timeout never resolves yesterday's findings. One audit a day (20 h), one GEO probe and one citation pass a week, each recorded in `settings` under `seo_*`.
- GEO: `probeGeo` asks DeepSeek (`DEEPSEEK_API_KEY`; skipped silently without it) the buyer questions in the desk's settings (`seo_geo_questions`) and keeps whether the answer named us, the URLs it cited and the companies it named instead (`seo_geo_runs`). `checkCitations` re-reads every `profile_url` weekly and keeps `link_verified_at` honest; a page that no longer links to us loses its verification, a page we could not read keeps it.
- Cycle: `ensureSeoCycle` files an approved system ticket on `malipetek-dev-site` (same shape as `ensureContentCycle`, `tickets.seo_cycle`) when `auto_cycle` is on and there are open findings at medium or above. The brief lists the five worst with host, path and detail, the site rules from this file, and the outbox contract. `finishSeoCycle` (called from `node.ts` and portal `run-result`, next to `finishContentCycle`) sets `ticket_id` on the findings it says it fixed, writes a `seo_events` `fix` row for each, stores profile drafts on `seo_citations.note` (through `SLOP`, so a draft in our name gets the post checks), and mails Ali with the PR.
- Ranks: once a week `runRanks` posts the `seo_rank_keywords` (max 25) to DataForSEO's Google Organic SERP API (standard queue, depth 100, `seo_rank_location`, default 2840/en), collects them over later cron ticks (`seo_rank_pending`), and writes one `seo_ranks` row per keyword: our best position or NULL outside the top 100, the URL, the top 10 domains and the task cost. The desk shows the weekly swing; it needs the `DATAFORSEO_API_KEY` secret (base64 of `login:password`, `npx wrangler secret put DATAFORSEO_API_KEY` in `worker/`), and skips with `rankReady:false` without it.
- Volatility hold: with `volatility_hold` on and a `core_update` event in the last 14 days (`POST /admin/seo/events`), the brief asks for technical fixes only and forbids rewriting copy that works. Google's rankings swing during a core update, and rewriting mid-swing hides what actually worked.
- API: `/admin/seo/overview`, `/pages`, `/findings`, `/geo`, `/ranks`, `/settings`, `/citations`, `/events` and `/run`, behind the admin session like `/admin/marketing/*`.

## Deploy
- **master is the deploy branch.** Cloudflare Workers Builds deploys three Workers from `malipetek/malipetek.github.io` on every push to master. There is no GitHub Actions deploy and no `CLOUDFLARE_API_TOKEN` repo secret; the builds use Cloudflare's own build token. Manage them with the signed-in `cf` CLI (`cf builds workers get|update`, `cf builds triggers list|update`).
  - `malipetek-site`: root `/`, build `pnpm install --frozen-lockfile`, deploy `pnpm run build && npx wrangler deploy --var BUILD_SHA:${WORKERS_CI_COMMIT_SHA}`.
  - `malipetek-intercom`: root `worker`, build `pnpm install --frozen-lockfile --ignore-workspace`, deploy `pnpm run build && npx wrangler deploy --var BUILD_SHA:${WORKERS_CI_COMMIT_SHA}` (no D1 migration yet; apply those separately).
  - `malipetek-sites`: root `/`, build `pnpm install --frozen-lockfile`, deploy `npx wrangler deploy -c sites-worker/wrangler.jsonc --var BUILD_SHA:${WORKERS_CI_COMMIT_SHA}`.
- The Cloudflare build does not run the test suite. Run `pnpm --dir worker test` before merging; typecheck and unit tests are the minimum.
- Migrations: add `worker/migrations/NNNN_name.sql`, then apply it with `npx wrangler d1 migrations apply malipetek-portal --remote` before the intercom build needs it. The intercom build currently only builds and deploys.
- Local deploys remain for break-glass only: `pnpm deploy` and `pnpm --dir worker deploy` build from the current checkout, so run them from a clean worktree. Normal deploys are Cloudflare Workers Builds.
- `.github/workflows/release.yml` is npm publishing for `packages/*`, not a deploy; it needs `NPM_TOKEN` or trusted publishing.
- Attachments/site deploys need the R2 buckets once: `npx wrangler r2 bucket create malipetek-portal-files` and `npx wrangler r2 bucket create malipetek-sites`.
- **Agents work in their own worktree**, never the shared checkout: `scripts/agent-worktree.sh <branch>` creates one from `origin/master` (under `~/.cache/malipetek-runner/worktrees/`) and prints its path. Commit there, push the branch, open a PR. One agent, one branch, one folder; the shared checkout stays clean for Ali.
- Health: `https://malipetek.dev/portal/admin#health` (web) or Harness → Admin → Health. The five-minute cron checks the callback and redirect URLs, each OAuth client's return address, every node's heartbeat and version, the live `BUILD_SHA` against master, project clone errors, stuck tickets and stopped site setup. It mails once when a check fails and once when it recovers; it is the only source of those alerts now.

## Fleet
- Nodes: MacBook (launchd `dev.malipetek.node`, runs from its own clean checkout `~/.cache/malipetek-runner/node-src/fleet`, so your working copy never decides what the node runs: after merging, `git -C ~/.cache/malipetek-runner/node-src fetch -q origin && git -C ~/.cache/malipetek-runner/node-src checkout -q --detach origin/master && launchctl kickstart -k gui/$(id -u)/dev.malipetek.node`) and G500 (`ssh DTNMachineG500`, systemd user unit `malipetek-node`, runs from the git checkout `~/malipetek-src/fleet`: after pushing, `ssh DTNMachineG500 'git -C ~/malipetek-src pull -q && systemctl --user restart malipetek-node'`). - Agents: every run goes through the Harness, so it has a conversation. ACP only where the account offers nothing else (Claude, Devin). Orders: `SYSTEM_ORDER` in `fleet/executors.mjs` and `worker/src/queue.ts` (keep them equal); picker labels: `AGENTS` in `packages/admin-ui/src/format.js`.

## Client sites (malipetek.online)
- Serving worker: `sites-worker/` (`malipetek-sites`, routes `*.malipetek.online/*` + apex). It deploys with everything else from master (the Deploy workflow); no separate manual deploy.
- Previews carry a feedback launcher (`public/preview-feedback.js`): note, voice note (transcribed by Workers AI Whisper) or annotated screenshot → a normal client ticket on that site's project. `sites-worker` injects it into preview HTML at serve time; client-Cloudflare previews get it at upload time (`worker/src/cloudflare-sites.ts`).
